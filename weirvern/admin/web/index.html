Four detectors watch the same traffic with different methods: Isolation Forest (outliers in feature space), Gradient Boosting (learned patterns from this deployment's own history), DBSCAN (dense-crowd clustering), and an adaptive per-host baseline. The ensemble asks how many of them AGREE before a score is believed. Check freshness first — a model scored against a stale baseline is still confident, just confident about the wrong traffic. The near-miss table is the honest way to judge a threshold: it lists the windows that almost alerted and why they did not. When each detector last retrained, and whether that is overdue. Sluice Gate

The gate is the part of this system that can STOP traffic, so it is built to fail open: if its supervisor dies, the gate OPENS rather than taking your network down — a tool that drops a production network when it has a bad day is a tool nobody deploys twice. The panel above always says which enforcement path is actually live, verified from the kernel, not from configuration. Rules are bounded by their duration and every block states its reason. Blocking on detections is off until you enable it in Settings → Sluice Gate. Block traffic by address, port or direction. Every rule is bounded -- this system does not create permanent blocks, so a rule that has lapsed shows here as lapsed rather than silently continuing to enforce. Blocking runs in the kernel on the weirling, so it does not slow the traffic it inspects.

Weirlings

A weirling is any sensor feeding this hub — a box running its own capture, or one exporting flows here. Registering records the EXPECTATION, so "the sensor you added never reported" can be told apart from "you have no sensors": two opposite facts that would otherwise look identical. Registration is a ledger, not an ingest switch — the hub always listens, and enforcement lives at the gate. The row marked local is this hub's own sensor; its runtime settings mount in its drill-down, because a sensor can only be configured on the box that runs it. The fleet: every weirling this hub expects to hear from, compared against what it has actually heard. A weirling is any additional capture point elsewhere in the network feeding this hub — a Zeek capture on another segment, or a box exporting flows to the collector. This view exists to tell you registered one and it never said anything apart from you have no weirlings, which are opposite facts that look identical everywhere else.

Register a weirling

Registering records the expectation, so a weirling that never comes up can be reported as missing rather than being invisible. It does not configure the remote box: nothing here can reach it, and a weirling begins reporting when its own exporter or Zeek instance points at this hub.
An address is refused rather than guessed: registering a network instead of one box would put a weirling at an address it does not have. Empty means not known yet, and the first heartbeat fills it in for display.

Runtime settings

Sonar surveys the network the capture interface is ON and pre-fills the siphon settings for you: it reads the interface's segment, sends one ARP sweep (the same "who has this address?" question every host on your LAN asks constantly) to find which addresses are alive and which are free, checks the gateway, and stages the result as pending changes below — segment, address, gateway, and targets. Nothing is written and nothing is intercepted: the recommendations are ordinary staged changes you can edit or discard, and they apply only when you press Apply.
A test run switches the sensor to siphon mode for 30 seconds, lets the worker run the real intercept (the same ARP-forge-and-relay your traffic would see), then switches back to loch and stops it — the mappings are restored on the worker's normal shutdown path. It is a probe, not a commitment: while it runs, Weirvern is genuinely in the traffic path for the hosts the plan names. It needs the siphon capabilities on the sensor node (the overlay), and a complete plan (segment, address, gateway, targets). The result below says which hosts were intercepted and that the mode was put back.
Edits here stage like every settings change: review and apply them in Settings → Pending changes.

Runtime settings live on the box that runs this sensor — nothing here can reach it. What you declare here (segment, expected mode) is the expectation this hub holds it to.

These are the values the running deployment is using, read from the cluster. Each setting is shown as the control that changes it — a toggle for on/off, a dropdown for a choice, a bounded number for a number — with an i in a circle beside every row explaining what it does and what happens when it moves.
