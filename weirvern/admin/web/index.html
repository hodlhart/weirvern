Sluice Gate

Block traffic by address, port or direction. Every rule is bounded -- this system does not create permanent blocks, so a rule that has lapsed shows here as lapsed rather than silently continuing to enforce. Blocking runs in the kernel on the sensor, so it does not slow the traffic it inspects.

Block a host or network

Refused on purpose: a rule with no address, a port without a protocol, the management interface, this sensor's own address, and anything covering the whole internet. Each refusal names the fix.

Blocking on detections

Whether the ensemble's own verdicts may block. Off by default: a tool that starts blocking on model output the moment it is installed would surprise anyone who installed it to watch first. The policy below is the operator's trust boundary, and each level states what it costs.

Weirlings

The fleet: every sensor this hub expects to hear from, compared against what it has actually heard. A weirling is any additional sensor elsewhere in the network feeding this hub — a Zeek sensor on another segment, or a box exporting flows to the collector. This view exists to tell you registered one and it never said anything apart from you have no sensors, which are opposite facts that look identical everywhere else.

Register a sensor

Registering records the expectation, so a sensor that never comes up can be reported as missing rather than being invisible. It does not configure the remote box: nothing here can reach it, and a sensor begins reporting when its own exporter or Zeek instance points at this hub.

An address is refused rather than guessed: registering a network instead of one box would put a sensor at an address it does not have. Empty means not known yet, and the first heartbeat fills it in for display.

Settings

loading…

These are the values the running deployment is using, read from the cluster. Each setting is shown as the control that changes it — a toggle for on/off, a dropdown for a choice, a bounded number for a number — with a ? beside every row explaining what it does and what happens when it moves. Who may change a setting depends on the account you signed in with: admins can stage and apply changes, and viewers see every value read-only. Secrets show as (set, N chars) or (not set), never in value. To change values without a web account, use weirvern config set, then apply.

Sensor

Sonar surveys the network the capture interface is ON and pre-fills the siphon settings for you: it reads the interface's segment, sends one ARP sweep (the same "who has this address?" question every host on your LAN asks constantly) to find which addresses are alive and which are free, checks the gateway, and stages the result as pending changes below — segment, address, gateway, and targets. Nothing is written and nothing is intercepted: the recommendations are ordinary staged changes you can edit or discard, and they apply only when you press Apply.

Pending changes

No changes staged. Edit a value above to stage one.

A test run switches the sensor to siphon mode for 30 seconds, lets the worker run the real intercept (the same ARP-forge-and-relay your traffic would see), then switches back to loch and stops it — the mappings are restored on the worker's normal shutdown path. It is a probe, not a commitment: while it runs, Weirvern is genuinely in the traffic path for the hosts the plan names. It needs the siphon capabilities on the sensor node (the overlay), and a complete plan (segment, address, gateway, targets). The result below says which hosts were intercepted and that the mode was put back.
